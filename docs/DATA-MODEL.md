# Data model

Everything in `data/` is generated by `scripts/build-data.mjs` from `scripts/taxonomy.mjs`. The contract below is enforced by `npm run verify:data` (67,990 checks).

## Files

| File | Purpose | Size |
| --- | --- | ---: |
| `manifest.json` | taxonomy, coordinates, edges, counts, asset paths | 112 KB |
| `search_index.json` | MiniSearch index over topics + channels | 176 KB |
| `video_index.json` | MiniSearch index over all 108,000 titles | 12.5 MB |
| `shards/<topic-id>.json` | videos for one topic | 60–4,604 records |
| `stats.json` | generated corpus statistics and digest | ~2 KB |
| `VERSION` | `1.0.0-<digest>` | 20 B |

## manifest.json

```jsonc
{
  "version": 1,
  "name": "YouTube Second Brain 100k",
  "generatedAt": "2026-11-13T09:03:46.453Z",
  "generator": "scripts/build-data.mjs",
  "seed": 20261113,
  "synthetic": true,
  "totals": { "videos": 108000, "topics": 480, "categories": 12, "channels": 312, "shards": 480 },
  "categories": [
    {
      "id": "architecture", "name": "LLM Architecture", "short": "Architecture",
      "hue": 265, "blurb": "How modern language models are wired inside.",
      "count": 11145, "centre": [2.2, 7.1, -2.8]
    }
  ],
  "topics": [
    {
      "id": "transformer_architecture", "name": "Transformer Architecture",
      "category": "architecture", "categoryName": "LLM Architecture",
      "count": 4604, "radius": 0.988,
      "pos": [2.204, 9.358, -4.176],
      "shard": "shards/transformer_architecture.json"
    }
  ],
  "edges": [[0, 1, 0.61], [0, 7, 0.44]],
  "assets": { "searchIndex": "search_index.json", "videoIndex": "video_index.json" },
  "schema": { "video": { "...": "documented below" } }
}
```

Invariants:

- `topics.length === 480`, 40 per category, unique `id` and `shard`.
- `sum(topics[].count) === sum(categories[].count) === totals.videos`.
- `pos` has exactly 3 finite numbers, all within ±16.
- `radius` is in `(0.05, 2)` and derived from count.
- `edges` are `[a, b, weight]` with valid distinct indices and `0 < weight ≤ 1.1`.
- `shard` is relative to `data/` and matches the topic id.

## shard files

```jsonc
{
  "version": 1,
  "id": "transformer_architecture",
  "name": "Transformer Architecture",
  "slug": "transformer_architecture",
  "category": "architecture",
  "categoryName": "LLM Architecture",
  "count": 4604,
  "generatedAt": "2026-11-13T09:03:46.453Z",
  "synthetic": true,
  "videos": [
    {
      "id": "gxrqcbnTUIw",
      "title": "When to Use Transformer Architecture — Benchmark Results",
      "channel": "Token Mechanics",
      "channelId": "ch_16",
      "duration": 2451,
      "views": 7200,
      "published": "2026-11-11",
      "type": "video"
    }
  ]
}
```

Rules:

- `videos.length === count`, sorted **newest first** (`published` desc, then `views` desc).
- `id` is a unique 11-character synthetic YouTube-style id (`[A-Za-z0-9_-]`).
- `duration` is integer seconds; `views` is a positive integer; `published` is `YYYY-MM-DD`.
- `type` ∈ `video | short | live | podcast`.
- Shard ids are globally unique across the corpus.

**Why order matters:** `video_index.json` stores the position of each video in its sorted shard. Re-sorting a shard without rebuilding the index will point search results at the wrong videos. `verify:data` samples this mapping, not all 108k documents.

## search_index.json

A serialised MiniSearch instance:

```js
new MiniSearch({
  idField: 'id',
  fields: ['name', 'categoryName'],
  storeFields: ['type', 'name', 'category', 'categoryName', 'count', 'slug'],
  searchOptions: { boost: { name: 3 }, fuzzy: 0.2, prefix: true }
})
```

Documents are topics (`id: "kw:<topic-id>"`, `slug` = topic id) and channels (`id: "ch_<n>"`, `type: "channel"`, `slug: "channel"`). The app filters results by `type === 'topic'`.

## video_index.json

```js
new MiniSearch({
  idField: 'id',          // numeric 0..107999
  fields: ['t'],          // title
  storeFields: ['k', 'n'] // topic array index, position in sorted shard
})
```

Resolution:

```js
const hit = index.search(q, { prefix: true, fuzzy: 0.15, limit: 40 })[0];
const topic = manifest.topics[hit.k];
const shard = await getShard(topic);
const video = shard.videos[hit.n];
```

Only four distinct shards are fetched per query, which bounds the cost of a cross-corpus search.

## Regenerating

```sh
npm run build:data -- --seed 20261113 --videos 108000
```

The generator is deterministic: same seed + taxonomy + target → same counts, coordinates, titles and digest. It removes and rewrites `data/` entirely.

Current snapshot: seed `20261113`, digest `5aef6e7764b219a2`, 108,000 videos, 480 topics, 312 channels, 958 edges, 21.4 MB of shards.

## Replacing the demo corpus

The UI only needs the schemas above. To ship real records:

1. Export one JSON object per video with the same fields (`id`, `title`, `channel`, `channelId`, `duration`, `views`, `published`, `type`).
2. Group by topic, sort newest first, write `data/shards/<topic-id>.json`.
3. Build `manifest.topics` with counts, shard paths and coordinates. Coordinates can be any layout — category centres + jitter is enough; the browser never simulates.
4. Build `search_index.json` and `video_index.json` with the exact MiniSearch options above, after sorting shards.
5. Run `npm run verify:data`. It is the contract test; fix everything it reports.
6. If your ids are real YouTube ids, change `youtubeSearchUrl()` in `index.html` to `https://www.youtube.com/watch?v=<id>`.

For genuinely large imports, shard the same way: one file per topic keeps a click under ~2 MB and keeps IndexedDB writes small.

## Synthetic-data disclosure

`manifest.synthetic` is `true` and every shard carries `synthetic: true`. Titles, channels, counts and views are generated; they do not describe real videos or real people. Links point to YouTube **search** results for the generated title, never to an unverified video id. Do not remove this disclosure without replacing the data.
